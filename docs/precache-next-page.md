# 預先翻譯下一頁（PRD / 設計）

狀態：提案，尚未實作。整體架構見 [design.md](design.md)。

## 1. 目標

現在翻頁後要等 10–15 秒譯文才會出現（§2.1），這是最大的痛點。讀目前這一頁時，就先把下一頁翻好存進快取；翻過去時直接命中快取，譯文在截圖完成後馬上畫上去（約 1.2 秒 debounce＋截圖，見 design.md §2.1）。

成功的樣子：照順序往後讀、每頁停留超過一次翻譯的時間時，**每一頁都命中快取**，不用再等 API。

### 1.1 不做的事

- 不預讀上一頁。往回翻通常是回去看剛讀過的頁，那一頁本來就在快取裡。
- 不預讀超過一頁（一個跨頁）。成本見 §3.7。
- 不在畫面上偷偷翻頁再翻回來截圖。翻頁動畫和閃爍會干擾閱讀，也會觸發 Kindle 的閱讀進度同步。
- 不開隱藏的第二個 Kindle 分頁或 iframe 去讀下一頁。要載入整個閱讀器、記憶體大，而且 Kindle 會以為有另一台裝置在讀，跳出「要跳到最新位置嗎」。
- 不自己向 Amazon 要頁面（§3.1 做法 B）。
- 第一版不支援看圖模式（方式 3，Opus 看截圖）。理由見 §3.5。

## 2. 現況

- **只看得到螢幕。** 所有頁面資料都來自 `captureVisibleTab`（`capture()`）。畫面上沒有的頁，背景程式拿不到。
- **快取用畫面指紋找。** `cacheGet(sig)` 拿截圖的指紋（`pageSigOf`）跟 `pageIndex` 逐一比 `samePage`。指紋是在書頁圖片範圍內、從**螢幕截圖**縮成 240 像素寬算出來的（design.md §3）。
- **區塊座標是截圖的比例。** `finishBlocks` 存的 `box` 是相對整個視窗的比例，`bg`／`fg` 從截圖取色。
- **已經有「等背景工作」的機制。** 翻回背景中的頁時，`backgroundResult` 會等它的 `done`，不重送（design.md §4.2）。預讀可以沿用。

### 2.1 一頁花多少時間

2026-10-27 從執行紀錄量的一頁（《愛麗絲夢遊仙境》，跨頁，精修模式）：

| 階段 | 時間 |
|---|---|
| 按鍵 → 送出 Haiku（debounce 1.2 秒、清掉譯文、截圖、OCR、版面） | 約 3.9 秒 |
| Haiku 翻譯（兩欄平行） | 約 5.7 秒 |
| Sonnet 校對 | 約 5 秒 |
| 合計 | 約 15 秒 |

只量了一兩頁，§7 步驟 0.5 再多量幾頁。不論數字多少，三段裡只有第一段的 debounce 和截圖在預讀後還會留著，其他都會消失。

### 2.2 Kindle Cloud Reader 怎麼載入書頁（2026-10-27 實測）

在《愛麗絲夢遊仙境》（B0C6HJ7TCR）、1529×992 的視窗、跨頁顯示下看到的：

- **DOM 裡只有目前這一頁。** 整個頁面只有一張書頁圖片，`div.kg-full-page-img > img`，`src` 是 `blob:` URL。沒有 iframe、沒有 canvas，畫面外也沒有預先放好的下一頁。
- **跨頁是一張圖。** 左右兩頁畫在同一張圖上：圖片原始大小 2450×1684，顯示在 1225×842 CSS 像素的範圍（`rasterScale=2`）。
- **書頁由伺服器畫好再傳下來。** 閱讀器向 `https://read.amazon.com/renderer/render` 要頁面，回應是 TAR（`packageType=TAR`），一次多頁。參數包括 `asin`、`revision`、字型、字級、行距、`width`／`height`（書頁範圍的 CSS 像素）、`theme`、`maxNumberColumns=2`、`rasterScale`、`startingPosition`、`numPage`、`skipPageCount`。
- **一次預先拿很多頁。** 開書時從同一個 `startingPosition` 發了 4 個請求：

  | `numPage` | `skipPageCount` | 大小 |
  |---|---|---|
  | 6 | 0 | 約 300 KB |
  | -6 | 0 | 約 43 KB |
  | 6 | 6 | 約 255 KB |
  | -6 | -5 | 約 3 KB |

  也就是往後約 12 頁、往前也有一些。開書的第一個請求參數不同（`width=1836`、`height=1338`，約 390 KB），之後的寬高跟畫面上的書頁一致。
- **翻頁不發請求。** 往後翻 3 個跨頁，一個 `render` 請求都沒有，但每次翻頁 `img` 的 blob URL 都換成新的。所以下一頁在翻之前已經在閱讀器的記憶體裡，翻頁時才做出新的 blob 放進 DOM。
- **同一組請求會整組重發。** 載入後約 36 秒和 66 秒，上面 4 個請求又各重發了一次。同時間 console 有 resize 的翻頁紀錄，推測是視窗大小變了、閱讀器按新尺寸重畫，未確認。

還不知道的：TAR 裡面的格式（一個檔是一頁還是一個跨頁、有沒有位置資訊）；往後翻幾頁才會補拿下一批。見 §7 步驟 0。

## 3. 設計

### 3.1 下一頁的畫面從哪裡來

原本打算從 DOM 讀出預先載入的下一頁圖片，但 §2.2 顯示 DOM 裡沒有。下一頁只存在閱讀器的記憶體裡，拿得到的方式有兩種：

**A. 旁聽閱讀器自己的 `render` 回應（採用）。**

- 新增一個跑在頁面 JS 環境（`"world": "MAIN"`）、`document_start` 載入的 content script，包住 `window.fetch`。請求網址是 `/renderer/render` 時，`clone()` 一份回應，把位元組用 `postMessage` 交給一般的 content script，原本的回應照常還給閱讀器。
- 一般的 content script 解開 TAR，保留最近一批的頁面圖片，依閱讀順序排好。
- 優點：
  - 不多發任何請求，Amazon 看到的流量跟現在完全一樣。
  - 拿到的就是翻過去後會顯示的那張圖，同樣的尺寸、字型、主題。指紋最有機會對得上（§3.2）。
- 缺點：
  - 依賴沒有公開的回應格式。Amazon 改了格式就會失效，要能偵測並安全地停用（§3.1.1）。
  - 要在閱讀器的程式取得 `fetch` 之前包好，所以必須 `document_start`、`MAIN` world。如果閱讀器改用 XHR 或 Web Worker 抓頁面，就旁聽不到。
  - 修改頁面的 `fetch` 比現在只讀 DOM 更侵入。包裝要做到出錯時完全不影響原本的請求。

**B. 自己呼叫 `render`（不採用）。**

- 照抄閱讀器的參數，`numPage=1`、`skipPageCount` 指到下一頁，從 content script 發請求（同網域，帶著使用者的 cookie）。
- 不採用的原因：
  - 每頁多一個請求，流量看起來不像一般閱讀。
  - 要自己算出下一頁的 `startingPosition`，還可能需要 CSRF token（看到閱讀器有呼叫 `/reader/api/csrf/getToken`）。
  - 自己去要書的內容，比旁聽更接近 README 提醒的「不要大量匯出書本內容」。

做法 A 也一樣只用下一頁，旁聽到的其他頁直接丟掉，不存、不送出。

#### 3.1.1 失效時的處理

下列任一情況都不預讀，執行紀錄寫出原因，翻譯照現在的方式在翻過去後才做：

- 沒有旁聽到任何 `render` 回應（閱讀器改了抓頁面的方式）。
- TAR 解不開，或裡面沒有可以辨認的圖片。
- 找不到目前這一頁在批次裡的位置（§3.2），或它已經是批次的最後一頁。

旁聽和解析的錯誤都要接住，不能讓閱讀器本身的請求或翻頁受影響。

#### 3.1.2 資料流

```
閱讀器 fetch(/renderer/render)
  → MAIN world 的包裝：clone，postMessage 位元組
  → content script：解 TAR、依順序保留這一批的圖片
  → background 要下一頁時（nextPage 訊息）：
      找出目前畫面在批次裡是第幾頁（§3.2），回傳下一頁的圖片
```

content script 新增的訊息：

```js
{ type: "nextPage", sig } → { dataUrl, width, height } | { error: "原因" }
```

`sig` 是目前畫面的指紋，用來在批次裡定位（§3.2）。`dataUrl` 用 PNG。

### 3.2 翻過去時怎麼對上快取

快取靠指紋找頁，而指紋是從螢幕截圖算的。預讀拿到的是原始圖片，要讓兩邊算出一樣的指紋：

- 把原始圖片縮放到它顯示時的大小，也就是目前的 `geometry.page`（CSS 像素）× `dpr`，就是截圖裡書頁的像素大小。再套用跟 `pageSigOf` 一樣的內縮（`SIG_INSET_PX`）、縮成 240 像素寬、取二值，用同一個 `pageSignature` 算指紋。
- 因為 §3.1 做法 A 拿到的就是會被顯示的那張圖，兩邊的差異只剩縮放方式和截圖的 JPEG 雜訊，預期遠低於 15% 的門檻。**要實測確認**（§7 步驟 0.3）。
- 預讀存進快取時用這個指紋，`cacheGet` 不用改。

同一套算法也用來**在批次裡定位**：對批次裡每一頁算指紋，跟目前畫面的指紋比，`samePage` 的那一頁就是目前這一頁，它的下一張就是下一頁。不需要解讀 TAR 裡的位置資訊。

原本考慮過用圖片的 blob URL 當第二把鑰匙，但 §2.2 看到每次翻頁 blob URL 都會換新，不能用。

不論如何，**畫上去之前都要再確認一次**：現有的「畫上譯文前再截一次圖」（design.md §3.3）照舊執行，不會把譯文畫到別頁上。

**視窗大小改變後**，閱讀器會用新尺寸重畫（§2.2 的整組重發）。舊尺寸的預讀結果指紋對不上，自然不會命中；進行中的預讀也直接取消，等新的一批到了再重新開始。

### 3.3 座標和顏色

預讀的 OCR 跑在原始圖片上，座標是圖片的像素，不是視窗的比例。

- 一張圖就是畫面上的書頁範圍（跨頁時也只有一張，§2.2），所以預讀的區塊存成**相對於書頁圖片的比例**。
- 讀取快取時用當下的 `geometry.page` 換算成視窗比例，再交給現有的 `showOverlay`。這一步在 background 做，`content.js` 的畫圖程式不用改。
- 快取 entry 多一個欄位標示座標是哪一種；前景翻譯的維持視窗比例，舊的 entry 不用遷移。
- `bg`／`fg` 從原始圖片取色，用現有的 `sampleBackground`／`sampleInk`（它們只需要 `{ width, height, pixels }`）。
- OCR 不用裁切，因為圖片本身就是書頁範圍；但跨頁仍然是一張圖，**照樣要 `findColumns`** 分欄。
- 原始圖片是 `rasterScale=2`，跟 3 倍解析度螢幕的截圖差不多大。超過 `OCR_MAX_PIXELS` 時等比例縮小，跟現在一樣。

### 3.4 排程

新增第三種工作：**預讀工作**。它跟前景工作、背景工作的關係：

| | 前景 | 背景 | 預讀 |
|---|---|---|---|
| 對象 | 畫面上這一頁 | 翻走前沒翻完的頁 | 下一頁 |
| 最多幾個 | 1 | 1（`MAX_BACKGROUND`） | 1 |
| 畫譯文／送側邊欄 | 會 | 不會 | 不會 |
| 會用 `captureVisibleTab` | 會 | 不會（已截過） | 不會 |

**什麼時候開始**，全部成立才開始：

1. 側邊欄開著、「翻頁自動翻譯」開著、「預先翻譯下一頁」開著、翻譯方式是 1 或 2（OCR）。
2. 目前這一頁的譯文已經畫上去（前景工作成功結束，或命中快取）。
3. 沒有背景工作在跑。背景工作是使用者翻走時還沒翻完的頁，它和預讀同時跑等於一次花兩頁的 API。
4. 在這一頁停了至少 2 秒（`PREFETCH_DWELL_MS`）。快速連續翻過已快取的頁時，不要每頁都發出預讀再取消。
5. 下一頁不在快取裡（用 §3.2 的指紋查）。

**翻頁時：**

- 翻到的正是預讀的那一頁、預讀還在跑：前景等它完成，沿用 `backgroundResult` 的做法（把預讀工作也放進它找的集合），不重送。
- 翻到的不是預讀的那一頁（往回翻、跳章節、拉進度條）：**取消預讀**。已經用掉的 token 照樣計費，但剩下的輸出不用付。被取消的工作不存快取。
- 判斷「是不是預讀的那一頁」用指紋比對。翻頁後的截圖本來就會做，不多花時間。

**跟手動翻譯的關係：** 按「翻譯這一頁」或 Alt+T 取消前景工作的行為不變，不動預讀。

**預讀失敗**（OCR 錯誤、API 錯誤、被拒、只給摘要）只寫進執行紀錄，不顯示紅字，不重試。翻過去後前景會照常翻譯，到時候再顯示錯誤。

**Service worker 被停掉：** 預讀工作跟前景一樣用 `keepAlive` 保持 worker 醒著。如果 worker 還是被停掉，預讀就消失了，翻過去時照常翻譯即可，不需要存進度。旁聽到的頁面存在 content script 裡，不受 worker 停掉影響。

### 3.5 看圖模式

方式 3 把整張截圖交給 Opus，回傳的座標是截圖的像素。換成原始圖片在技術上可行（座標改成圖片的比例，§3.3），但：

- Opus 一頁比方式 1、2 貴很多，預讀錯頁的浪費也比較大。
- 送出的是書頁圖片，不是整個閱讀器畫面。提示詞和 `MAX_EDGE` 的縮圖規則要重新驗證。

所以第一版只做方式 1、2。實作完後如果看圖模式也需要，另外評估。

### 3.6 介面與執行紀錄

- 執行紀錄：
  - 「預讀下一頁：開始」、「預讀完成：X 秒，n 段，已存快取」、「預讀取消：翻到別頁」、「沒有預讀：原因」（沒有旁聽到頁面、批次裡找不到目前這一頁、背景工作在跑、方式 3 等）。
  - 旁聽到 `render` 回應時記一行：幾頁、大小。方便確認旁聽還有效。
  - 命中預讀的頁時寫「命中快取（預讀）」，跟一般的快取命中分開，方便統計命中率。
- 側邊欄：預讀不改狀態列，不顯示「翻譯中」，避免使用者以為目前這頁還沒好。
- 設定頁加一個「預先翻譯下一頁」開關，**預設開啟**。這個功能的目的就是讓翻頁不用等；關掉的選項給在意 API 用量的人。

### 3.7 成本

預讀翻的頁，大多數是使用者接下來本來就會讀的頁，所以不是額外的成本，只是提早花。真正浪費的是「預讀了但沒讀到」的頁：

- **停止閱讀時**：最後一頁的下一頁，每次閱讀最多浪費一頁。
- **往回翻、跳頁時**：取消當下已用掉的 token。一頁的翻譯在 15 秒內做完，通常早就做完了，所以這種情況多半浪費整頁。
- **同一頁停留不到 2 秒就翻走**：不會開始預讀（§3.4 條件 4）。

一般的連續閱讀（每頁 1–2 分鐘，順著往後讀）浪費接近 0。最差的情況是一直來回翻、每頁都停超過 15 秒，此時 API 用量最多變成兩倍。

## 5. 驗收條件

1. 照順序往後讀、每頁停留 20 秒以上時，從第二頁起，翻過去的頁都命中快取，譯文在截圖後 1 秒內畫上。
2. 跨頁和單頁顯示都成立。
3. 往回翻、跳章節時，進行中的預讀被取消，執行紀錄寫出原因，新的頁照常翻譯。
4. 翻到正在預讀的頁時，等它完成，不另外送一次 API 請求。
5. 側邊欄關著、自動翻譯關著、方式 3、預讀開關關著時，都不預讀。
6. 旁聽失效（沒有回應、格式不對）時，不預讀，執行紀錄寫出原因，閱讀器本身和其他翻譯行為都跟現在一樣。
7. 預讀的譯文畫上去時位置正確，跟前景翻譯同一頁的結果對齊（誤差在幾個像素內）。
8. 背景工作在跑時不開始預讀。
9. 擴充功能不會對 Amazon 發出任何閱讀器本身沒有發的請求。
10. 翻頁偵測、譯文的開關、Kindle 自己重繪的處理都跟現在一樣。

## 6. 待決定

- **停留門檻 2 秒**：要不要更長。太長會讓「讀得快的頁」等不到預讀，太短在快速翻頁時浪費。上線後看執行紀錄的取消次數再調。
- **預讀的頁要不要也校對**：目前設計跟前景一樣，精修模式就送 Sonnet 校對。預讀有整頁的時間可以用，沒有理由降低品質。
- **能不能接受包住頁面的 `fetch`**（§3.1 做法 A）：這是這個設計唯一可行的來源。如果不能接受，就只剩縮短單頁時間的做法（例如先畫 Haiku 初稿、校對完再更新），那是另一份設計。

## 7. 工作分解

步驟 0 和步驟 6 的實測需要使用者登入的 Kindle Cloud Reader、在 Chrome 載入的擴充功能和 API key，只能在本機做。其他步驟不需要。

**0. 調查（本機）**

實測前先關掉側邊欄的「翻頁自動翻譯」，否則每翻一頁都會呼叫 API。

- 0.1 ~~下一頁的圖片是否在 DOM 裡~~：不在，見 §2.2。
- 0.2 TAR 的格式：裡面有哪些檔、一個圖片檔是一頁還是一個跨頁、圖片格式、有沒有位置資訊。單頁顯示時再看一次。
- 0.3 把旁聽到的下一頁圖片縮放後算指紋，跟翻過去後截圖的指紋比較，確認遠低於 15%。單頁、跨頁、深色主題各一組。
- 0.4 閱讀器是不是在載入後才取得 `fetch`（決定 `document_start` 的包裝能不能攔到）；往後翻幾頁才會補拿下一批；視窗大小改變時是不是整組重發。
- 0.5 多量幾頁的時間組成（§2.1）。

**1. 旁聽**
- 1.1 `page-hook.js`：包住 `fetch`，只處理 `/renderer/render`，出錯時不影響原本的回應。
- 1.2 `manifest.json` 加上 MAIN world 的項目。
- 1.3 `content.js`：接收、解 TAR、保留最近一批。
- 1.4 測試：TAR 解析（用步驟 0.2 存下的樣本，只用沒有版權的書）、格式不對時安全失敗。

**2. 翻譯原始圖片**
- 2.1 `ocrPage` 接受原始圖片：不裁切、照樣分欄。
- 2.2 區塊座標存成圖片比例（§3.3），從原始圖片取色。
- 2.3 讀取快取時換算成視窗比例。

**3. 指紋與定位**
- 3.1 用原始圖片算指紋（§3.2）。
- 3.2 在批次裡找出目前這一頁、回傳下一頁（`nextPage`）。
- 3.3 測試：定位成功、找不到、目前這一頁是批次最後一頁。

**4. 排程**
- 4.1 預讀工作：開始條件（§3.4）、停留門檻、最多一個。
- 4.2 翻到預讀中的頁時等它完成（擴充 `backgroundResult`）。
- 4.3 翻到別頁、視窗大小改變時取消。
- 4.4 測試：連續往後讀都命中、往回翻取消、跳頁取消、翻到預讀中的頁不重送、背景工作在跑時不預讀、各種開關關著時不預讀。

**5. 設定與介面**
- 5.1 設定頁的開關。
- 5.2 執行紀錄（§3.6）。

**6. 驗證**
- 6.1 單元測試通過。
- 6.2 （本機）讀一個章節，確認 §5 的驗收條件，特別是命中率和譯文位置。
- 6.3 （本機）單頁、跨頁、深色主題、改變視窗大小後各試一次。
- 6.4 （本機）確認沒有多出任何對 Amazon 的請求（DevTools 的 Network）。
