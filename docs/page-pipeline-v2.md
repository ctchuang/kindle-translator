# 新的頁面流程：攔下閱讀器的頁面資料、段落快取、預讀下一頁（PRD / 設計）

狀態：提案，尚未實作。現行架構見 [design.md](design.md)。

## 1. 目標

1. **翻頁不用等。** 現在翻頁後要等 10–15 秒譯文才會出現（§2.1），這是最大的痛點。讀目前這一頁時就先把下一頁翻好，翻過去時直接畫上。
2. **用精確的頁面身分取代截圖指紋。** 現在靠截圖的粗略指紋判斷「是不是同一頁」，為了容忍工具列、游標、JPEG 雜訊，周圍長出了 `overlaySig`、`lastSig`、`sigCrop`、清掉譯文後等重畫再截圖等一整套機制。改成直接知道畫面上是哪一頁（位置編號），這些都可以拿掉。
3. **以段落為單位快取。** 翻過的段落在任何版面下都能重用。改字級、改視窗大小、往回翻、翻譯途中換頁，都只需要翻還沒翻過的段落。

做法是旁聽閱讀器自己向 Amazon 拿頁面資料的回應（§3.1），用裡面的資料自己把頁面畫出來（§3.2），再用它判斷畫面上是哪一頁（§3.3）、給 OCR 讀（§3.4）。

### 1.1 不做的事

- 不對 Amazon 發出任何閱讀器本身沒有發的請求。只旁聽，不自己要頁面。
- 不在畫面上偷偷翻頁再翻回來，因為會打斷閱讀，也會讓閱讀器的閱讀進度和閱讀速度紀錄失真。
- 不開隱藏的第二個 Kindle 分頁或 iframe。
- 不預讀超過一頁，不預讀上一頁。
- 不從頁面資料直接讀出文字：字形只有編號，沒有對應的字元（§2.3）。文字仍然由 OCR 讀出。
- 看圖模式（方式 3）的翻譯方式不變，仍然把截圖交給 Opus；只是頁面身分和快取改用新的做法（§3.8）。

## 2. 現況與實測

### 2.1 一頁花多少時間

2026-10-27 從執行紀錄量的一頁（《愛麗絲夢遊仙境》，跨頁，精修模式）：

| 階段 | 時間 |
|---|---|
| 按鍵 → 送出 Haiku（debounce 1.2 秒、清掉譯文、截圖、OCR、版面） | 約 3.9 秒 |
| Haiku 翻譯（兩欄平行） | 約 5.7 秒 |
| Sonnet 校對 | 約 5 秒 |
| 合計 | 約 15 秒 |

只量了一兩頁，§7 步驟 0 再多量幾頁。

### 2.2 Kindle Cloud Reader 怎麼載入書頁（2026-10-27、28 實測）

在《愛麗絲夢遊仙境》（B0C6HJ7TCR）、跨頁顯示下看到的：

- **DOM 裡只有目前這一頁。** 整個頁面只有一張書頁圖片，`div.kg-full-page-img > img`，`src` 是 `blob:` URL。沒有 iframe、沒有 canvas，畫面外也沒有預先放好的下一頁。跨頁時左右兩頁畫在同一張圖上。
- **每翻一頁，`img` 都換一個新的 blob URL。** 翻頁時不發網路請求，下一頁是從閱讀器記憶體裡的資料當場畫出來的。
- **頁面資料來自 `https://read.amazon.com/renderer/render`。** 回應是 TAR，一次 6 個畫面（`numPage=6`，跨頁時一個畫面就是一個跨頁）。參數包括 `asin`、`revision`、字型、字級、行距、`width`／`height`（書頁範圍的 CSS 像素）、邊界、`theme`、`maxNumberColumns`、`rasterScale`、`startingPosition`、`numPage`、`skipPageCount`。
- **閱讀器大約維持往後 12 個畫面的緩衝。** 開書時從同一個位置發 4 個請求：往後 `skip=0`、`skip=6` 各 6 個畫面，往前也拿一些。往後讀時每用掉約 6 個畫面補拿下一批（這次在翻到第 6 個畫面時要了 `skip=12`，再往後要了 `skip=18`）。視窗大小改變時，整組請求依新尺寸重發。
- **頁面載入後才包住 `window.fetch` 也攔得到。** 閱讀器每次都透過 `window.fetch` 發請求，沒有事先存下原本的 `fetch`。

### 2.3 TAR 的內容

沒有圖片，全是 JSON：

| 檔案 | 內容 |
|---|---|
| `page_data_<i>_<j>.json` | 每個畫面一項：`width`／`height`（CSS 像素）、`startPositionId`／`endPositionId`、`fillColor`、`inkColor`，以及 `children`：文字串（`run`）和插圖（`image`） |
| `glyphs.json` | 每種字型（`fontKey`）的字形向量輪廓（SVG path）、`unitsPerEm` |
| `tokens_<i>_<j>.json` | 每個畫面的區塊，每塊有位置範圍、外框，以及每個字的位置範圍和外框 |
| `layout_data_*`、`layout.json`、`panels_*`、`toc.json`、`manifest.json`、`metadata.json` | 還沒細看 |

一個文字串（`run`）有：`transform`（位置）、`glyphs`（字形編號陣列）、`xPosition`（每個字形的 x）、`fontKey`、`fontSize`、`fontWeight`、`fontStyle`、`textColor`、`startPositionId`／`endPositionId`、`rect`。字形編號是字型內部的編號，沒有對應的 Unicode 字元，所以讀不出文字。

插圖（`image`）有 `transform`、`rect` 和 `imageReference`。圖片本身另外從 CDN 載入，不在 TAR 裡。

### 2.4 自己畫出來的頁跟閱讀器的一樣

用 canvas 照 `run` 把字形畫出來（`Path2D(path)`，依 `fontSize / unitsPerEm` 縮放，放在 `transform` 加上 `xPosition` 的位置，`rasterScale=2`）：

- 跟閱讀器顯示的 `img` 逐像素比較，**插圖以外的 490 萬個像素沒有一個不同**。
- 每翻一頁，比對結果最接近的都正好是批次裡的下一張，所以可以用來找出畫面上是哪一頁。
- 如果改用現在的指紋（縮成 240 像素寬、15% 門檻）比對，插圖的灰階在縮小時會滲到周圍，有插圖的頁差異有 56–75%。所以要在原尺寸下比對，而且把插圖排除在外（§3.3）。

## 3. 設計

### 3.1 旁聽頁面資料

- **`page-hook.js`（新）**：`manifest.json` 裡的第二個 content script，`"world": "MAIN"`、`"run_at": "document_start"`。包住 `window.fetch`：網址是 `/renderer/render` 時，`clone()` 一份回應，把位元組和請求參數用 `postMessage` 交給一般的 content script，原本的回應照常還給閱讀器。包裝裡的任何錯誤都接住，不影響原本的請求。
- **`content.js`** 接收、解開 TAR，只保留 `page_data` 和 `glyphs`（`tokens` 是否需要見 §3.4），依請求參數分組：
  - **版面鑰匙**（`layoutKey`）：`asin`、`revision`、字型、字級、行距、`width`、`height`、邊界、`theme`、`maxNumberColumns`、`rasterScale`。同一個位置在不同版面下會排成不同的畫面，所以「哪一頁」一定要連同版面鑰匙一起說。
  - 同一個版面鑰匙下的畫面依 `startPositionId` 排序、去重。換了版面鑰匙（視窗大小、字級、主題改了）就丟掉舊的。
  - 最多保留約 30 個畫面，超過時丟掉離目前這頁最遠的。
- 旁聽到的資料只用於目前這頁和下一頁，不存、不送出擴充功能以外的地方。

### 3.2 畫出頁面

`renderPage(page, glyphs, scale)`：在 canvas 上依 §2.4 的方式畫出所有 `run`。

- 背景用 `page.fillColor`，字的顏色用每個 `run` 的 `textColor`，所以跟閱讀器的主題一致。
- 插圖不畫。這對 OCR 反而比較好：插圖裡的標籤本來就不翻譯（design.md §5.4），現在根本不會被讀到。
- 寫成不依賴 DOM 的純函式（只用 `OffscreenCanvas` 和 `Path2D`），放在新檔 `page-render.js`，content script、offscreen 文件和 Node 測試共用。

### 3.3 畫面上是哪一頁

**偵測換頁**：content script 用 MutationObserver 看 `.kg-full-page-img img` 的 `src`。換了就是閱讀器重畫了畫面，可能是翻頁，也可能是同一頁重畫（視窗大小、主題）。

**辨識**：把 `img` 跟目前版面鑰匙下的候選畫面逐一比對：

1. 先比尺寸：`img` 的原始大小必須等於 `page.width × rasterScale` 和 `page.height × rasterScale`。
2. 從上一次辨識到的畫面往前後找，通常第一個候選就中。
3. 在原尺寸下，把候選畫面畫出來跟 `img` 逐像素比，插圖範圍（由 `image` 的 `transform` 和 `rect` 算出）排除在外。不同的像素少於 0.1% 就算同一頁，留一點空間給抗鋸齒的細微差異。
4. 只有插圖、沒有文字的畫面，再比插圖的數量和位置。仍然分不出來時視為辨識失敗。

結果是**頁面身分**：`{ layoutKey, startPositionId, endPositionId }`。content script 把它連同畫面在視窗中的位置（`img` 的 `getBoundingClientRect`）送給 background（`pageShown` 訊息）。

**辨識失敗**（沒有旁聽到資料、批次裡沒有這一頁、比對不上）：content script 送 `pageShown { error }`，側邊欄顯示紅字原因，這頁不翻譯。常見原因是擴充功能在閱讀途中重新載入，錯過了先前的批次，重新整理 Kindle 分頁即可。刻意不退回截圖流程，理由同 design.md §5.3：同樣的頁面因環境不同而有不同結果，會很難除錯；兩條流程並存也違背這次簡化的目的。見 §6。

這取代了：截圖指紋（`page-sig.js`）、`sigCrop`、`CONTENT_CROP`、`lastSig`、`overlaySig`、`shownSig`、`detachIfPageChanged` 的重新截圖比對，以及翻譯完成後「再截一次圖確認還是同一頁」。

### 3.4 OCR 與段落

- **輸入**：§3.2 畫出的頁面，不是截圖。不需要先清掉譯文、等畫面重畫，也不需要 `ocrCrop`、`OCR_CROP`：頁面本身就是書頁範圍。
- **在哪裡畫**：offscreen 文件。background 把這一頁的 `page_data` 和用到的字形（從 content script 取得）交給 offscreen，offscreen 畫好直接 OCR，不用來回傳圖片。
- **分欄、Tesseract、DocLayout-YOLO、分段**：照現在的流程（design.md §5）。跨頁仍然是一張圖，照樣用 `findColumns`。
- **段落的位置範圍**：OCR 分好的每一段，找出外框落在段落框裡的 `run`，取最小的 `startPositionId` 和最大的 `endPositionId`，就是這一段的**位置範圍**。
- **段落的外框**：改用這些 `run` 的外框聯集（精確到像素），不用 OCR 的框。`lines` 用不同基線的數目算。

**待確認（§7 步驟 0）**：`tokens` 的區塊是不是就是段落。如果是，可以直接用它的位置範圍和外框分段，連 DocLayout-YOLO 都可能不需要。實測時看到一個區塊的外框橫跨左右兩頁，可能是一段從左頁接到右頁，框被合在一起，所以要確認。在確認之前，設計以 OCR＋DocLayout-YOLO 分段為準。

### 3.5 段落快取

鑰匙和內容：

```js
// chrome.storage.session
"para:<asin>:<revision>:<start>-<end>" → { source, text, kind, savedAt }
"page:<layoutKey>:<startPositionId>" → { paras: [{ start, end, kind }], savedAt }
```

- **段落**存原文和譯文，跟版面無關：同一個位置範圍在任何字級、視窗寬度下都是同樣的文字。
- **頁**存這個畫面在這個版面下分成哪幾段（OCR 和分段的結果），省掉同一頁再 OCR 一次。不存座標，座標每次從 `run` 算（§3.4），所以視窗只是移動位置時也不用重算。
- 被頁緣切斷的段落，在不同版面下切點不同、範圍也不同，就是不同的鑰匙，要重翻。完整的段落都能重用。
- 上限：段落 5,000 個、頁 500 個，超過時丟掉最舊的。
- 摘要（design.md §6.2）不存，跟現在一樣。

**顯示一頁**：

1. 用頁面身分查 `page:`。沒有就 OCR、分段，存 `page:`。
2. 每一段查 `para:`。全部都有就直接畫。
3. 缺的段落送給 Claude（翻譯和校對照現在的做法），回來的結果逐段存 `para:`，再畫。

**手動「重新翻譯本頁」**：略過這一頁所有段落的 `para:`，結果覆蓋舊的。按鈕的標籤改看「目前畫面的頁面身分是不是已經畫上譯文」，不再比指紋。

### 3.6 翻譯工作與排程

**一個工作就是「翻譯一組段落」**，結果一律逐段存進快取，不管畫面已經換到哪裡。工作分三種：

| | 前景 | 背景 | 預讀 |
|---|---|---|---|
| 對象 | 畫面上這一頁缺的段落 | 翻走時還沒翻完的段落 | 下一頁缺的段落 |
| 最多幾個 | 1 | 1 | 1 |
| 完成時畫譯文 | 會（如果還是同一頁） | 不會 | 不會 |

- **翻頁時不取消**：前景工作改成背景，繼續翻完、存快取。已經用掉的 token 不會浪費，結果在任何版面下都用得上。背景超過 1 個時，才取消最舊、而且不屬於目前畫面的那個。
- **翻到正在翻的段落**：新的前景工作只送還沒有人在翻的段落；正在背景或預讀中翻的段落等它們完成，不重送。
- **畫上去之前**：只要比對頁面身分，content script 回報的目前頁面還是這一頁才畫。content script 自己也會再檢查一次：畫譯文的訊息帶著頁面身分，跟目前的不同就丟掉。這取代了現在的翻頁計數（`turn`）。
- **debounce**：畫快取裡的譯文不等，換頁就畫。要送 API 的工作仍然在最後一次換頁後 1.2 秒才開始，快速連續翻頁時中間的頁面不會送出。

**預讀**的開始條件，全部成立才開始：

1. 側邊欄開著、「翻頁自動翻譯」開著、「預先翻譯下一頁」開著。
2. 目前這一頁的譯文已經畫上。
3. 沒有背景工作在跑。
4. 在這一頁停了至少 2 秒（`PREFETCH_DWELL_MS`）。
5. 批次裡有下一個畫面，而且它有段落不在快取裡。

預讀的頁也要 OCR 和分段。它的 OCR 在 offscreen 文件裡進行，不會擋住畫面。預讀失敗只寫進執行紀錄，不顯示紅字，不重試。

**跳頁、往回翻**：預讀不取消，照樣翻完存快取；如果新的前景工作因此要等名額，才取消預讀。理由跟翻頁時不取消一樣：已經付了的 token，結果留著比較划算。

### 3.7 畫上譯文

- 段落的外框是頁面座標（CSS 像素，相對於書頁圖片），由 content script 依 `img` 目前在視窗中的位置換算，所以背景程式不再需要知道視窗大小。
- 底色用 `page.fillColor`，字色用段落中最多字的 `run` 的 `textColor`。不再需要 `sampleBackground`、`sampleInk`。
- `showOverlay`、`fitText` 和字級的規則不變（design.md §7）。

### 3.8 看圖模式

方式 3 仍然截圖交給 Opus，因為它要看整個畫面，包括插圖。改變的只有：

- 頁面身分用 §3.3，不再算指紋。
- 快取：Opus 回傳的是區塊和譯文，沒有原文，所以存成整頁一筆（`vision:<layoutKey>:<startPositionId>`），座標是書頁圖片的比例，不能跨版面重用。

截圖相關的程式（`capture`、截圖佇列、清掉譯文再截圖）只剩這個模式和「存下截圖」在用。

### 3.9 介面與執行紀錄

- 執行紀錄：
  - 旁聽到 `render` 回應：幾個畫面、大小、版面是否改變。
  - 辨識：頁面身分（位置範圍）、比對了幾個候選、花多少毫秒；失敗時的原因。
  - 段落快取：這頁幾段，幾段命中、幾段送出、幾段正在別的工作裡翻。
  - 預讀：開始、完成（秒數、段數）、略過的原因。
- 側邊欄：預讀不改狀態列。辨識失敗時顯示紅字，提示重新整理 Kindle 分頁。
- 設定頁：「預先翻譯下一頁」開關，預設開啟。

### 3.10 成本

- **預讀**：預讀的頁大多是接下來本來就會讀的。浪費的是停止閱讀時的最後一頁，以及跳頁、往回翻時已經預讀好但沒讀到的頁。一般的連續閱讀浪費接近 0；最差的情況（一直來回翻、每頁都停超過 15 秒）API 用量最多兩倍。
- **段落快取**省下的：改字級、改視窗大小後重讀，只需要重翻頁緣被切斷的段落；翻譯途中換頁的結果不再浪費。

## 5. 驗收條件

1. 照順序往後讀、每頁停留 20 秒以上時，從第二頁起，譯文在換頁後 0.5 秒內畫上。
2. 同一頁重畫（工具列進出、滑鼠移動、Kindle 自己更新進度）時，不清掉譯文、不重新翻譯。
3. 改變字級或視窗大小後，回到讀過的位置時，只有頁緣被切斷的段落送出 API。
4. 翻譯途中翻頁，那些段落仍然翻完並存進快取；翻回來時不重送。
5. 往回翻、跳章節時，新的頁照常翻譯；需要名額時才取消預讀。
6. 側邊欄關著、自動翻譯關著、預讀開關關著時，都不預讀。
7. 辨識失敗時，側邊欄顯示原因，閱讀器本身不受影響；重新整理 Kindle 分頁後恢復。
8. 譯文的位置跟原文段落對齊，誤差在 1 CSS 像素內。
9. 單頁、跨頁、白／米色／深色主題都成立。
10. 擴充功能不會對 Amazon 發出任何閱讀器本身沒有發的請求（DevTools 的 Network 確認）。
11. 看圖模式照常運作。

## 6. 待決定

- **辨識失敗時要不要退回截圖流程**：設計是不退回（§3.3），程式只有一條路。代價是格式一改就整個不能用，直到擴充功能更新。如果覺得風險太高，可以保留現在的截圖流程當備案，但要接受兩套流程並存。
- **`tokens` 能不能取代 OCR 分段**：看步驟 0 的結果。能的話 DocLayout-YOLO 可能整個不需要（75 MB 下載、WebGPU 需求都可以拿掉），但那是另一個改動，不放在這次。
- **快取要不要跨瀏覽器重開**：段落快取跟版面無關，很適合放 `chrome.storage.local` 長期保存（[reference-pages.md](reference-pages.md) 也需要 1 週的保存）。這次先維持 session storage，跟現在一樣。
- **停留門檻 2 秒**：上線後看執行紀錄再調。
- **測試資料**：TAR 裡有 Amazon 字型（Bookerly）的字形輪廓，不能放進公開的 repo。測試用的 TAR 要自己產生：用一個開源字型的字形輪廓，照同樣的 JSON 格式組出假的頁面資料。
