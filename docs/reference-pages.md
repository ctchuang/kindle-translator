# 校對時參考前面的頁與人名對照表（PRD / 設計）

狀態：已實作，預設關閉。參考段落（2.2.0）在《Ender's Game》上實測過 20 頁（§9）；人名對照表（§10，2.3.0）是那次實測之後加的，還沒實測。整體架構見 [design.md](design.md)。

這份文件原本寫在 2.0 之前，靠頁尾的頁碼排序、在 session 快取裡多存原文。2.0 的[新頁面流程](page-pipeline-v2.md)已經有書的識別碼（`asin`、`revision`）和位置編號，段落快取也已經存了原文和譯文，所以改寫成以段落為單位、用位置編號排序。

## 1. 目標

精修模式（Haiku 初稿 + Sonnet 校對）一次只看一頁，所以人名、專有名詞、稱呼和語氣在頁與頁之間常常不一致。這個功能把同一本書在本頁之前讀過的段落（原文 → 定稿的譯文）送給 Sonnet 當參考，讓校對能對齊前面的譯法。

參考段落只能涵蓋最近幾頁，實測時人名仍然會在超出範圍、或沒經過校對的地方跑掉（§9），所以再加一份每本書的人名對照表（§10），同一個開關控制。

這是一個實驗：預設關閉，用設定開啟，並在執行紀錄留下足夠的資訊，方便比較開和關的品質和成本。

### 1.1 不做的事

- 不改 Haiku 初稿的 prompt，參考段落只給 Sonnet 校對。
- 不支援快速模式（沒有校對）和看圖模式（沒有 OCR 原文）。
- 不做術語表或超過 1 週的長期記憶。
- 不把本頁之後的段落當參考，以免 Sonnet 用到使用者還沒讀到的內容（往回翻時也一樣）。

## 2. 參考段落從哪裡來

**只存畫上去的段落。** 譯文畫到頁面上（或覆蓋層關閉時顯示在側邊欄）時，把這個畫面每一段的原文和最後的譯文存起來（`saveReference`，在 `draw` 裡）。所以：

- 參考的是使用者讀過的、校對後的定稿，不是預讀但還沒讀到的頁。
- 從快取畫上的畫面也會存，所以開關打開之前翻過、這次瀏覽器還沒關的頁，翻回去看一次就會成為參考。
- 只給摘要的結果不存。

**以段落為單位，跟版面無關。** 跟段落快取一樣用位置範圍（`start`–`end`）當身分。同一段在不同字級下位置範圍一樣（page-pipeline-v2.md §2.4），所以改字級、改視窗大小都不影響。被頁緣切斷的段落在不同版面下範圍不同：新存的段落跟舊的有重疊時，舊的換成新的（`mergeParas`）。

**存在 `chrome.storage.local`，保留 1 週。** Session storage 關掉瀏覽器就清掉，不夠用：

| 鍵 | 內容 |
|---|---|
| `ref:<asin>:<revision>` | `{ paras: [{ start, end, source, text, savedAt }], refStart }`，依位置排序 |
| `refBooks` | 每本書最後一次寫入的時間，用來刪掉 1 週沒讀的書 |

- 每次寫入時刪掉超過 7 天的段落，以及 7 天沒有寫入的書。每本書最多 2000 段，超過時丟掉最早存的。
- 2000 段約 1–2 MB，`chrome.storage.local` 的 10 MB 上限放得下幾本書，所以沒有加 `unlimitedStorage`。
- 寫入一個個排隊（`refChain`），讀改寫不會互相覆蓋。
- `source` 跟送給 Claude 翻譯的一樣，可能帶 `<i>`、`<b>`、`<h1>` 標記（[text-styles.md](text-styles.md)）。
- 書的原文和譯文會在使用者的硬碟上保存 1 週。設定頁有「刪除已存的參考段落」按鈕，README 也有寫。

## 3. 挑選參考段落（`context-pages.js`）

純函式，`background.js` 用 `importScripts` 載入，Node 測試直接 `require`。

`pickReference(paras, at, refStart, maxTokens)`，`at` 是本頁的起始位置：

1. 只挑 `end < at` 的段落：本頁之前，不含本頁。
2. 參考集從 `refStart` 開始，往後讀時新的段落接在最後，前面不變。
3. 超過 `maxTokens` 時，一次丟掉最舊的段落直到剩一半以下，`refStart` 移到剩下的第一段。不是每頁丟一段：快取是 prefix 比對，開頭一換後面全部要重寫。
4. 重新起算（沒有 `refStart`、本頁在 `refStart` 之前、或範圍內沒有段落）時，從本頁往前取到 `maxTokens` 的一半，留空間往後長。
5. 跳過的頁只是留下空缺，不重新起算：往後跳幾章，前面的人名照樣有用。

時間只用來決定保存期限，不當排序條件：用語一致跟書裡的距離有關，跟時間無關。

Token 數用字元估（`estimateTokens`）：中日韓文字一字一個，其他 3.5 字元一個，再加每段 8 個給 JSON。估算偏高。

## 4. 送給 Sonnet

### 4.1 校對改成一頁一次

以前一頁分兩段，各自翻譯後各自校對。現在兩份初稿都完成後，整頁送一次校對（`reviewDrafts`）。翻譯仍然分兩段平行跑。

- 校對只輸出要改的段落，通常幾百 tokens，時間主要在首個 token 之前，拆開省不了多少；大約多一段校對的時間（幾秒）。
- 參考段落只送一次，沒有兩個請求同時寫入快取；Sonnet 看得到整頁，雙頁版面左右兩頁的用語也能一起統一。
- 這一項跟開關無關，精修模式都是一頁一次。
- 校對失敗時沿用整頁初稿。Opus 補翻的那一半不送校對，另一半照樣校對。

### 4.2 Content 的順序

```
[說明（固定）] [參考段落 block 1] … [block n] [本頁的校對 prompt]
```

- 參考段落每行一段：`{"source": …, "text": …}`，依位置排序。
- **切成約 1000 tokens 一個 block**（`referenceBlocks`），滿了就封起來。Prompt caching 是在 block 邊界比對 prefix，如果整個參考集是一個 block，每多一段內容就變了，永遠不會命中。
- **兩個 cache breakpoint**：最後一個封起來的 block，以及最後一個 block。往後讀時封起來的 block 不變，所以每頁讀一次快取、只寫入最後那個還在長的 block；一個 block 封起來時寫入它，下一頁就從它讀。往回找快取最多 20 個 block，一次只多一兩個 block，找得到。
- 校對 prompt 加一條規則（`REFERENCE_RULE`）：參考段落已經定稿，人名、專有名詞、稱呼和語氣以它為準；不要修改或翻譯參考段落，corrections 只能列本頁的 id；本頁的意思以本頁原文為準，不要用參考段落補完被切斷的段落。
- 參考段落沒有 id，所以 Sonnet 就算想改也列不出來；不在本頁的 id 本來就會被丟掉。
- 快取 TTL 用預設的 5 分鐘：讀取會重新計時，一般每 1–2 分鐘翻一頁，快取會一直有效。

### 4.3 執行紀錄

- 送了參考段落：`校對參考前面的頁：N 段（位置 a–b），約 T tokens`，重新起算或丟掉一半時另外註明。
- 沒送：`校對沒有參考前面的頁：` 加原因（不知道是哪一本書、這本書在本頁之前還沒有翻過的段落）。開關關閉時不寫。
- 每個 API 請求的「回應結束」那一行，有快取讀寫時加上 `快取讀 X / 寫 Y`（`cache_read_input_tokens`、`cache_creation_input_tokens`）。

## 5. 成本

單價（Claude API 文件，2026-10）：Sonnet 5.5 一般輸入 $2/MTok；寫入快取（5 分鐘 TTL）$2.5；讀取快取 $0.20。

原本假設一頁約 1,200 tokens。實測（§9）雙頁一個畫面約 3,000–3,500 tokens，所以每翻一頁新寫入快取的量就有約 3,500 tokens（約 $0.009），這是主要的成本，跟上限 R 幾乎無關；R 影響的是每頁讀快取的量，以及多久丟一次一半。

**每翻一頁，參考段落多出的成本（以一個畫面 3,500 tokens 計）**

| 上限 R | 約幾個畫面 | 快取命中（連續閱讀） | 快取失效（休息後第一頁） |
|---|---|---|---|
| 10k（預設） | 2–3 | 約 $0.011 | 約 $0.025 |
| 16k | 4–5 | 約 $0.013（實測估算） | 約 $0.040 |
| 32k | 9 | 約 $0.015 | 約 $0.080 |

- 快取命中：讀參考集（R/2 到 R，$0.20/MTok），加上寫入新的畫面（約 $0.009）；丟掉一半的那一頁要重寫 R/2。
- 對照：每頁的 Sonnet 校對約 $0.008。校對改成一頁一次，提示詞的部分也省了一份。
- 人名對照表（§10）只送這一頁出現的名字，通常十幾個，每個請求多不到 200 tokens，成本可以忽略。

## 6. 設定

- 設定頁「校對時參考前面的頁（實驗）」，預設關閉，同時控制參考段落和人名對照表；「參考段落的上限（tokens）」，預設 10000（原本 16000，有了人名對照表之後降低），範圍 2000–100000。都存在 `chrome.storage.sync`（`referencePages`、`referenceTokens`）。
- 「刪除已存的參考段落和人名對照表」：刪掉 `chrome.storage.local` 裡所有書的參考段落和人名對照表，立即生效。
- 開關只決定存不存、送不送；關掉後已存的資料留到到期（段落 1 週、人名 30 天），或按刪除。

## 8. 待決定

- **本頁之後的段落**：往回翻時，後面已經讀過的段落要不要也當參考？目前不送。
- **1 小時 TTL**：休息時間常落在 5–60 分鐘的話，1 小時 TTL（寫入 $4/MTok）可能比較划算。看執行紀錄裡快取失效的次數再決定。
- **對照表要不要收專有名詞**（地名、組織，例如 Battle School）：目前只收人名。
- **改錯的譯名**：先到先贏，第一次就翻錯的人名會一直錯，目前只能按「刪除」整份重來。之後可以在側邊欄列出對照表、讓使用者修改。

## 9. 實測：《Ender's Game》20 頁（2026-10-30）

參考段落開啟、上限 16000、精修模式，從第 4 章〈LAUNCH〉開頭往後翻 20 個雙頁畫面，每頁停約 20 秒。

- **快取有命中**：連續閱讀時每頁「快取讀」1–1.6 萬、「快取寫」3–5 千 tokens。超過上限丟掉一半的 4 次，那一頁「快取讀 0 / 寫約 1 萬」，下一頁又恢復命中。
- **一個畫面比估計大**：約 3,000–3,500 tokens，所以 16000 只裝得下 4–5 個畫面（§5 已更新）。估計的 token 數比 API 實際少約 5%。
- **人名大致一致**：「安德」出現約 260 次只錯 1 次；格拉夫、瓦倫丁、彼得、沈、斯蒂爾森完全一致。執行紀錄裡看得到 Sonnet 依參考段落把 Haiku 初稿的「柏納德」「恩德」改回「伯納德」「安德」。
- **還有 8 處不一致**，原因有三種：

| 原因 | 例子 |
|---|---|
| Haiku 以版權為由拒絕，那一欄改由 Opus 翻譯，不經校對（20 頁裡發生 3 次） | 「阿萊」（應為「艾萊」）×10、「戴普」（應為「達普」） |
| Sonnet 漏改一兩處 | 「恩德」、「葛拉夫」、1 處「阿萊」 |
| 第一次出現就翻成另一種，之後兩種並存 | Wiggin：第 1–2 頁「威金」，第 3 頁起「維金」 |

三種都是人名對照表（§10）要解決的：Opus 補翻也拿得到對照表；校對的 prompt 明確列出這一頁該用的譯名；先到先贏，不會有第二種譯法。

### 9.1 加上人名對照表後再跑一次（2026-10-30）

同一段 20 頁，參考段落上限 10000，對照表從空的開始。開頭時閱讀器先停在第 69 頁，那一頁在跳回第 4 章前就翻好了，所以 Ender、Valentine、Alai、Bernard、Dap 等名字一開始就在表裡。

- **8 處不一致只剩 1 個名字**：安德 ×263、葛拉夫、伯納德、艾萊、達普、瓦倫汀、彼得、沈、史提森全部一致。第 15 頁又有一欄由 Opus 補翻，這次照對照表翻成「艾萊」「達普」（上次是「阿萊」「戴普」）。
- **Wiggin 還是混用**（第 1–2 頁「懷金」，第 3 頁起「維金」）：對照表同時存了「Wiggin → 懷金」（第 1 頁）和「Ender Wiggin → 安德・維金」（第 69 頁的派令 "ENDER WIGGIN"）。英文字串不同，所以沒被當成衝突；出現全名的頁兩條都送出，Sonnet 照全名那條改（校對說明：「Ender Wiggin 的譯名（懷金→安德・維金）」）。所以改成只存單一名字（§10）。
- 參考段落上限 10000 時，丟掉一半更頻繁，那一頁「快取寫」約 6.5 千（16000 時約 1 萬）。

### 9.2 只存單一名字之後（2026-10-30）

參考段落上限 16000，從第 3 章〈GRAFF〉開頭往後翻，到第 29 頁時 session storage 滿了，之後每頁都翻譯失敗（design.md §5，已修），所以只有 29 頁。對照表在新版載入前、用舊版翻第一頁時就存了「Ender → 恩德」「Graff → 格拉夫」「Valentine → 華倫蒂」，之後一路沿用。

- **Wiggin 29 頁全部是「威金」**，名和姓分開存之後沒有再出現兩種譯法。
- 約 600 次人名只剩 3 處各錯一次：「安德」（恩德 ×約 390）、「葛拉夫」（第 1 頁的章名「GRAFF」，格拉夫 ×50）、「史提森」（史提爾森 ×10）。都是單次漏改，不是換成另一套譯法。
- 「葛拉夫」那一次，Sonnet 有回報 Graff → 葛拉夫，程式也發現了衝突，但只保住了對照表，畫上去的還是「葛拉夫」。所以加上改回對照表譯名的步驟（§10）。
- 「恩德」「華倫蒂」不是台灣通行的譯名，但照先到先贏一直沿用：第一次就定錯的名字會一直錯（§8）。

## 10. 人名對照表

每本書一份英文人名 → 譯名的對照表，由 Sonnet 校對時整理，之後每次翻譯和校對都照它翻人名，不受參考段落上限的影響。跟參考段落同一個開關。

- **收集**：開關打開時，校對的 JSON schema 多一個 `names`（`REVIEW_NAMES_SCHEMA`），請 Sonnet 列出這一頁原文出現的每個人名和定稿譯文用的譯名，名和姓分開各列一項，不列全名、不含稱謂。地名、組織等不收（§8）。
- **只存單一名字**（`splitNames`）：Sonnet 還是回了全名時，英文按空白、譯名按間隔號（・、· 等）拆開，數目一樣就逐一配對（「Mazer Rackham → 梅澤·拉克姆」存成 Mazer → 梅澤、Rackham → 拉克姆），對不上的不存（「Mr. Wiggin → 威金先生」）。全名和它的部分各存一條會互相矛盾（§9.1）；拆開之後，全名裡的姓跟已有的譯名不同就是一般的衝突，照先到先贏處理。之前存下的全名讀表時直接丟掉。給模型的規則也說明：對照表只有單一的名或姓，全名把各部分用「・」接起來。
- **存放**：`chrome.storage.local` 的 `names:<asin>:<revision>` → `{ names: { <原名>: { text, savedAt } } }`。索引 `nameBooks`。
- **先到先贏**（`mergeNames`）：已經有的名字不改譯名，Sonnet 回報不同的譯法時寫進執行紀錄（「已有別的譯法，沿用原本的」）。名字再出現時重新計時。
- **改回對照表的譯名**（`restoreNames`）：Sonnet 回報的譯名跟對照表不同，表示這一頁的譯文用了別的譯名。在原文含有這個名字的段落裡，把那個譯名換成對照表的（「葛拉夫」→「格拉夫」），不用再呼叫 API。一個字的譯名不換（「申」會換到「申請」），譯名是對照表譯名的一部分時也不換。Sonnet 沒有回報的不一致抓不到（§9.2 的「安德」「史提森」可能就是）。
- **保存期限**：每個名字最後一次出現後 30 天；30 天沒讀的書整份刪掉。每本書最多 500 個名字。
- **使用**（`namesIn`）：只送這一頁原文裡以完整單字出現的名字（`Ender's` 算 Ender，`Peterson` 不算 Peter），放進：
  - Haiku 初稿和 Opus 補翻的 prompt：「人名一律照這份對照表翻譯」。實測裡 Opus 補翻的那一欄不經校對，是人名跑掉最多的地方。
  - Sonnet 校對的 prompt：同一句，初稿不一致時要改。
- **放在哪裡**：在本頁的 prompt 裡，也就是參考段落的 cache breakpoint 之後。對照表會變長，放在前面會讓參考段落的快取每次都失效。
- 讀寫失敗時照常翻譯，只是不用對照表。
- 快速模式（沒有校對）會用已經存下的對照表，但不會新增。
