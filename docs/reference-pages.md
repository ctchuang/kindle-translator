# 校對時參考前面的頁（PRD / 設計）

狀態：提案，尚未實作。整體架構見 [design.md](design.md)。

## 1. 目標

精修模式（Haiku 初稿 + Sonnet 校對）一次只看一頁，所以人名、專有名詞、稱呼和語氣在頁與頁之間常常不一致。這個功能把同一本書最近翻過的頁（原文 → 譯文，附頁碼）連同本頁頁碼一起送給 Sonnet 當參考，讓校對能對齊前面的譯法。

這是一個實驗：預設關閉，用設定開啟，並在執行紀錄留下足夠的資訊，方便比較開和關的品質和成本。

### 1.1 不做的事

- 不改 Haiku 初稿的 prompt，參考頁只給 Sonnet 校對。
- 不支援看圖模式（Opus 看截圖）：那條路徑沒有 OCR 原文。
- 不做術語表或超過 1 週的長期記憶。參考頁只保留 1 週（§3.2）。
- 不把本頁之後的頁當參考（見 §6），以免 Sonnet 用到使用者還沒讀到的內容。

## 2. 現況

- **快取只有譯文。** `cacheSet(sig, blocks)`（`background.js`）存的是畫覆蓋層用的 blocks：`kind`、`lines`、`text`（譯文）和座標。OCR 原文在 `ocrTranslator` 裡用完就丟了。
- **快取不分書。** 索引是 `pageIndex = [[id, sig], ...]`，只靠頁面指紋找頁，沒有記錄是哪一本書。
- **沒有頁碼。** 截圖時會裁掉頁尾（見 design.md §5.1），而 `content.js` 目前也不讀頁面上的任何文字。
- **校對一次一段。** 一頁分成最多兩段（`splitParas`），各自由 Haiku 翻譯，再由 `reviewChunk` 交給 Sonnet 平行校對（§3.4 改成一頁一次）。
- `callClaude` 的 `content` 已經是 content block 陣列，可以直接在某個 block 上加 `cache_control`。

## 3. 設計

### 3.1 頁面資訊

`content.js` 從 Kindle Cloud Reader 的 DOM 讀出：

- `book`：書的識別碼，取自網址的 `asin` 參數。
- `page`：頁尾 "Page X of Y" 的 X，沒有就是 null。
- `location`：頁尾 "Location N" 的 N，沒有就是 null。

background 在截圖前向頁面要這份資訊，連同 `sig` 一起帶進 job。雙頁版面時記下左頁的頁碼。

**待確認（§7 步驟 0）**：頁尾在 DOM 裡的實際位置和文字格式、雙頁時顯示的是哪一頁、換書時 `asin` 會不會跟著變。這幾點要在實際頁面上看過才能寫 selector。

排序用的「位置」：有 `page` 就用 `page`，否則用 `location`。兩者都沒有時，這一頁不當參考，本頁也不送參考頁（§6 待決定）。

### 3.2 快取格式與保存期限

參考頁保留 1 週，不能再只放在 `chrome.storage.session`（關掉瀏覽器就清掉）。做法：

- 畫面快取（`pageIndex` 和 `page:<id>`）維持在 session storage，行為不變。
- 另外在 `chrome.storage.local` 存一份參考頁：每本書一個 key（例如 `ref:<book>`），內容是該書各頁的位置、`savedAt` 和原文／譯文對照，不存座標。
- 寫入時順便刪掉 `savedAt` 超過 7 天的頁，以及 7 天內都沒有更新的書。
- `chrome.storage.local` 預設上限 10 MB。一頁約 5 KB，一般閱讀量放得下；`manifest.json` 是否加 `unlimitedStorage` 由實作時量測決定。
- 書的原文和譯文會在使用者的硬碟上保存 1 週，README 的說明要寫清楚。

session storage 裡的 cache entry 從 blocks 陣列改成物件：

```js
{
  book: "B0XXXXXXX",      // asin，讀不到就是 null
  page: 23,               // 或 null
  location: 345,          // 或 null
  savedAt: 1761400000000,
  blocks: [{ kind, lines, text, source, x0, y0, x1, y1 }, ...],
}
```

- 每個 block 多一個 `source`（OCR 原文），由 `ocrTranslator` 填入。
- `cacheGet` 照舊回傳 blocks，呼叫端不受影響。
- 舊格式的 entry（陣列、沒有 `source`）照常用來重畫，但不拿來當參考，不需要遷移。

### 3.3 挑選參考頁

寫成不依賴瀏覽器的純函式（例如新檔 `context-pages.js`，跟 `page-sig.js` 一樣用 `module.exports` 給 Node 測試）：

```js
pickReferencePages(entries, current, { maxTokens }) → [{ page, location, pairs: [{ source, text }] }, ...]
```

規則：

1. 只挑 `book` 和本頁相同、且有 `source` 的 entry，排除本頁本身（指紋相同或位置相同）。
2. 只挑位置在本頁之前的頁，由近到遠加入，直到估計的 token 數超過 `maxTokens`。
3. 結果依位置由舊到新排序。
4. Token 數用字元數估算（不另外呼叫 count_tokens API）。英文約 4 字元 1 token，中文約 1 字 1 token，估算偏保守即可。

**為了讓 prompt cache 命中，參考集要穩定。** 快取是 prefix 比對，參考集的開頭只要換了一頁，後面整段都要重新寫入。所以不要每翻一頁就滑動一頁：

- 往後讀時，新翻完的頁接在參考集最後，前面不變。
- 超過上限時，一次丟掉最舊的一半，而不是每次丟一頁。
- 實作方式：在 `ref:<book>` 裡記下目前參考集的起點（`refStart`，一個位置）。挑選時只考慮位置 ≥ `refStart` 的頁；超過上限就把 `refStart` 往後移到剩一半的地方。跳到別的章節（本頁位置比 `refStart` 還前面，或離參考集太遠）時重設 `refStart`。

時間只用來決定保存期限（1 週，§3.2），不當排序條件：用語一致跟書裡的距離有關，跟時間無關。

### 3.4 校對改成一頁一次

現在一頁分兩段，每段的 Haiku 初稿完成後各自送一次 Sonnet 校對。改成兩份初稿都完成後，整頁送一次校對。翻譯仍然分兩段平行跑。

- **為什麼可以合併：** 翻譯要輸出整頁譯文，時間花在 decoding，所以拆開平行有好處。校對只輸出要改的段落，通常只有幾百 tokens，時間主要在首個 token 之前，拆開省不了多少。
- **延遲：** 從「兩段各自的初稿＋校對取較慢者」變成「較慢的初稿＋一次校對」，大約多一段校對的時間，通常幾秒。Sonnet 大幅改寫半頁時會比較慢，從執行紀錄的「校對完成：X 秒，改了 n/m 段」確認。
- **好處：** 參考頁只送一次，成本約減半；沒有兩次請求同時寫入快取的競爭；Sonnet 看得到整頁，雙頁版面左右兩頁的用語也能一起統一。
- 校對失敗時沿用整頁初稿，跟現在一樣。Opus 補翻過的段落仍然不送校對。

這一項不依賴參考頁，可以先單獨上線（§7 步驟 4.1）。

### 3.5 送給 Sonnet

校對的 content 改成兩個 text block：

1. **參考頁**，加上 `cache_control: { type: "ephemeral" }`（5 分鐘 TTL）。依序列出每一頁的頁碼，以及該頁各段的原文和譯文（JSON，鍵的順序固定）。
2. **本頁的校對 prompt**：現在的 `buildReviewPrompt`，加上本頁頁碼和以下規則：
   - 參考頁是同一本書前面已經定稿的譯文，用來統一人名、專有名詞、稱呼和語氣。
   - 不要修改或翻譯參考頁，corrections 只能列本頁的段落。
   - 本頁的意思以本頁原文為準，不要用參考頁的內容補完本頁被切斷的段落。

參考頁放在最前面，是為了讓它成為穩定的 prefix；本頁內容每次都不同，放在 cache breakpoint 之後。

`callClaude` 的變更：

- 從串流的 `message_start` / `message_delta` 讀出 `usage`，在執行紀錄印出 `cache_read_input_tokens`、`cache_creation_input_tokens` 和 `input_tokens`。
- content 已經是陣列，不需要改介面。

只在精修模式且開關打開時生效。Haiku 初稿、Opus 補翻（`translateChunk` 的備援）都不送參考頁。

### 3.6 成本

主要的限制是參考頁的輸入 token 數（上限 R）。Prompt caching 的 TTL 和 §3.2 的 1 週保存期限是兩回事：API 的快取最長 1 小時。

單價（Claude API 文件，2026-10）：Sonnet 5.5 一般輸入 $2/MTok；寫入快取在 5 分鐘 TTL 是 $2.5、1 小時 TTL 是 $4；讀取快取 $0.20。最低可快取長度 512 tokens。

假設一頁的原文、譯文加 JSON 約 1,200 tokens（估計值，步驟 0.3 實測；雙頁版面乘以 2），每頁送一次校對（§3.4）。

**每翻一頁，參考頁多出的成本**

| 上限 R | 約幾頁 | 不用快取 | 快取命中（連續閱讀） | 快取失效（休息後第一頁） |
|---|---|---|---|---|
| 8k | 7 | $0.016 | $0.005 | $0.020 |
| 16k | 13 | $0.032 | $0.006 | $0.040 |
| 32k | 27 | $0.064 | $0.009 | $0.080 |
| 64k | 53 | $0.128 | $0.016 | $0.160 |

- 快取命中：讀一次快取，加上寫入新接上的那一頁（約 $0.003）。滿了丟掉一半時要重寫，平均攤下來每頁也是約 $0.003。
- 參考集在 R/2 到 R 之間來回，平均約 0.75R，表上偏保守。
- 對照：現在每頁的 Sonnet 校對約 $0.008。

讀 300 頁、中間休息 10 次（每次都讓快取失效），16k 約 $2.3。

**TTL 用 5 分鐘。** 讀取會重新計時，一般每 1–2 分鐘翻一頁，快取會一直有效。1 小時 TTL 每頁的寫入比較貴（約 $0.005），只有休息時間常落在 5–60 分鐘時才划算。上線後看執行紀錄的失效次數再決定。

快取要等寫入的那次請求開始回應後才讀得到。一頁只送一次校對，不會有同一頁的請求互相競爭。

### 3.7 設定與介面

- 設定頁（`options.html/js`）：
  - 「校對時參考前面的頁」開關，預設關閉。
  - 參考頁的 token 上限，預設 16000。
  - 存在 `chrome.storage.sync`，跟其他設定一樣。
- 執行紀錄：這次送了哪幾頁（頁碼）、估計的 token 數、API 回報的快取讀寫量；沒送參考頁時說明原因（開關關閉、讀不到頁碼、沒有同一本書的頁等）。

| `background.js` | 帶頁面資訊進 job、快取新格式、`chrome.storage.local` 的參考頁、`ocrTranslator` 保留原文、校對改成一頁一次並加參考頁、`callClaude` 記錄 usage |

## 5. 驗收條件

1. 開關關閉時，除了校對改成一頁一次（§3.4），行為跟現在一樣。
2. 開關打開、同一本書連續往後讀時：
   - 第二頁起，Sonnet 的請求帶有前面的頁，依頁碼由舊到新。
   - 第三頁起，`cache_read_input_tokens` 接近參考頁的大小。
3. 關掉瀏覽器重開後，同一本書 1 週內翻過的頁仍然會當參考；超過 1 週的不會。
4. 換書後，第一頁不帶任何參考頁。
5. 跳到前面的章節後，不會帶跳轉前（位置在本頁之後）的頁。
6. 讀不到頁碼時不送參考頁，執行紀錄寫出原因，翻譯本身照常完成。
7. Sonnet 的 corrections 不包含參考頁的段落（id 不在本頁就丟掉，現有邏輯已經這樣做）。
8. 參考頁不超過設定的 token 上限。

## 7. 工作分解

步驟 0 和步驟 6 的實測需要使用者登入的 Kindle Cloud Reader、在 Chrome 載入的擴充功能和 API key，只能在本機做。其他步驟不需要。

**0. 調查（本機）**
- 0.1 在實際頁面找頁尾頁碼的 DOM 位置和格式（Page / Location），以及雙頁時顯示哪一頁。結果寫回 §3.1。
- 0.2 確認換書時網址的 `asin` 會不會變。
- 0.3 量幾頁英中對照的 token 數，確認 16000 的預設上限大約是幾頁，並更新 §3.6 的成本表。

**1. 頁面資訊**
- 1.1 `content.js` 讀取 `{ book, page, location }`，讀不到就回 null。
- 1.2 `background.js` 截圖前取得頁面資訊，帶進 job。
- 1.3 執行紀錄顯示書和頁碼。

**2. 快取格式**
- 2.1 entry 改成 §3.2 的物件格式，`cacheGet` 照舊回傳 blocks。
- 2.2 `ocrTranslator` 回傳的 blocks 保留 `source`。
- 2.3 相容舊格式的 entry。
- 2.4 `chrome.storage.local` 的參考頁存放和 1 週清理（§3.2）。

**3. 挑選參考頁**
- 3.1 新增 `context-pages.js`，實作 §3.3。
- 3.2 參考集起點 `refStart` 的維護（跟參考頁一起存在 `ref:<book>`）。
- 3.3 單元測試（`tests/context-pages.test.js`，`npm test`）：換書、往後讀、超過上限時丟掉一半、跳到前面、沒有頁碼、舊格式 entry。

**4. 送給 Sonnet**
- 4.1 校對改成一頁一次（§3.4）。不依賴其他步驟，可以先單獨上線，用執行紀錄比較前後的時間。
- 4.2 校對的 content 改成 §3.5 的兩段。
- 4.3 校對 prompt 加上本頁頁碼和參考頁規則。
- 4.4 `callClaude` 記錄 usage 和快取讀寫量。
- 4.5 只在精修模式且開關打開時送參考頁。

**5. 設定與介面**
- 5.1 設定頁的開關和上限。
- 5.2 執行紀錄的參考頁資訊。

**6. 驗證**

- 6.2 （本機）讀一個章節，開和關各翻一次，比較人名、用語的一致性和 Sonnet 改了幾段。
